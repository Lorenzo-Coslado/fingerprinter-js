# Ecosystem expectations and v3 decisions

Reviewed on **9 November 2026**. These references establish practical expectations for a browser fingerprinting package. They do not certify FingerprinterJS, prove detection accuracy, or imply feature parity with a hosted identity service. No external service is required by this project.

## Comparable projects have different purposes

| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |

| [BotD](https://github.com/fingerprintjs/BotD/blob/main/README.md)                                                                                                                                                                                                           | Browser-side basic automation detection under MIT. Its maintenance policy prioritizes stability; the repository separates the client package from the commercial API product.                         | Distinguish automation indicators from malicious intent; prioritize regression coverage and maintainable rules.                  |
| [CreepJS](https://github.com/abrahamjuliot/creepjs/blob/master/README.md)                                                                                                                                                                                                   | Research and education about fingerprinting and privacy defenses. The project explicitly says it is not intended to be an integration library.                                                        | Make browser observations and changes inspectable. ## What integrators ask for

The following are concrete examples from primary documentation and public issue reports. They are qualitative evidence of integration pain, not a survey or a claim about its frequency. A report in another project's issue tracker is not independently reproduced here.

| Need                                              | Primary evidence                                                                                                                                                                                                                                                                                           | Decision for v3                                                                                                                                                                                                 |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Installation that works in the actual application | [FingerprintJS API](https://github.com/fingerprintjs/fingerprintjs/blob/master/docs/api.md) documents npm, browser modules, script tags and CommonJS. [Issue 602](https://github.com/fingerprintjs/fingerprintjs/issues/602) describes an import failing during Next.js SSR because it accessed `window`.  | Test the packed package through ESM, CommonJS and TypeScript consumers. Defer browser access until collection; document browser-only execution separately from safe server-side imports.                        |
| An operation that eventually settles              | [Issue 1235](https://github.com/fingerprintjs/fingerprintjs/issues/1235) reports `get()` waiting indefinitely after temporary iframe removal during navigation.                                                                                                                                            | Central per-collector deadlines, an overall budget, explicit partial results and cancellation. Clean up DOM nodes, timers and browser resources even on failure.                                                |
| An explanation when an identifier changes         | [Issue 809](https://github.com/fingerprintjs/fingerprintjs/issues/809) reports a changing Safari HDR component. The [version policy](https://github.com/fingerprintjs/fingerprintjs/blob/master/docs/version_policy.md) describes identifier compatibility boundaries and transitional old/new collection. | Separate the hash schema from the package version, identify the active projection and expose component-level comparison. Changes in environment or schema are explainable, not silently called fraud.           |
| Honest uniqueness limitations                     | [Issue 1130](https://github.com/fingerprintjs/fingerprintjs/issues/1130) reports identical identifiers from different devices. FingerprintJS's [limitations](https://github.com/fingerprintjs/fingerprintjs/blob/master/readme.md#limitations) distinguish browser hashing from hosted identification.     | Describe the fingerprint as an environment signature. A SHA-256 output is not evidence that its input is unique. Do not use the signature alone as authentication, authorization or an automatic fraud verdict. |
| Inspectable, typed collection failures            | [FingerprintJS result API](https://github.com/fingerprintjs/fingerprintjs/blob/master/docs/api.md) returns component value/error and duration, not only an opaque identifier.                                                                                                                              | Provide typed `ok`, `unsupported`, `blocked`, `timeout`, `error`, `aborted` and `excluded` states with duration. Collection coverage describes availability, not identity accuracy.                             |
| Control over effects and data collection          | The [FingerprintJS API](https://github.com/fingerprintjs/fingerprintjs/blob/master/docs/api.md) and [BotD API](https://github.com/fingerprintjs/BotD/blob/main/docs/api.md) document their optional monitoring requests and how to disable them.                                                           | Keep library collection free of telemetry and network requests by default. Explain storage probes and every optional network collector; do not silently contact a hardcoded STUN server.                        |
| Predictable upgrades                              | The [FingerprintJS version policy](https://github.com/fingerprintjs/fingerprintjs/blob/master/docs/version_policy.md) explicitly addresses identifier changes, including stability fixes within a minor line.                                                                                              | Document API SemVer separately from fingerprint-schema compatibility, ship migration examples and retain deterministic fixtures for the schema.                                                                 |

## Interpretation of the v3 analysis

The analyzer replays the `userAgent` and optional `automation` snapshot. It never reads the current `window`, `navigator`, permissions, locale or screen. Explicit WebDriver, tool and headless observations form one automation group, avoiding repeated weighting of the same underlying evidence. A declared crawler user agent is labeled as an unverified declaration, not a malicious actor.

Its 0–100 score is a heuristic weight. `LOW` does not establish that a visitor is human, and `HIGH` does not prove malicious intent. Analysis `status` is `complete` when a usable user agent and at least one explicit boolean automation observation are supplied, `partial` when only one is available, and `insufficient` when neither is available. This describes the analyzer's two inputs, not the completeness of every browser collector. Excluded or blocked collectors do not create suspicion. Collection success, missing APIs, language/timezone combinations, privacy defenses and software rendering are not bot evidence in these rules. Rules carry a separate version for deterministic replay.

The [W3C Privacy Working Group guidance](https://www.w3.org/TR/fingerprinting-guidance/) recommends minimizing exposed information and degrading gracefully for privacy-conscious users. This is a design reference, not a certification or a legal exemption. Deployment-specific purpose, notice, consent and retention remain integration decisions.

## Release acceptance criteria

- One short, working quick start, then progressive access to configuration and diagnostics.
- No required account, remote API, telemetry or runtime dependency.
- Every exported entry exists in the distributed archive and has compatible declarations.
- Tests fail if all fingerprints become the same constant or if intended identification inputs are ignored.
- Timeouts, cancellation, unsupported APIs and concurrent collections have defined outcomes.
- The demo runs the built SDK locally, performs real repeatability checks and distinguishes fixtures from browser observations.
- Documentation explains what enters the hash, what stays outside it, what causes a signature to change and how to migrate.
- Browser test results describe the tested engines and conditions. Longitudinal accuracy, false-positive rates and collision rates require separate population evidence before quantitative claims.

Features such as a hosted device graph, signed server findings, mobile-native identification or a calibrated fraud model are separate product work. Matching their names in a browser API would not reproduce their guarantees.
